# StudyHub — Phase A2 report: materials (TXT / PDF / DOCX), chunks, search

Scope (from [STUDYHUB-DESIGN.md](STUDYHUB-DESIGN.md) §5, §12): files become searchable chunks with page numbers and topics;
a scanned PDF is reported, not silently empty. **Not in this phase:** web URLs, answering questions, quizzes, progress,
and no model is called anywhere in A2.

## What exists

| Piece | File |
|---|---|
| Type detection by content, text extraction with page and heading locators | `studyhub/extract.py` |
| Heading-aware chunks (~900 chars, never across a heading) and topics | `studyhub/chunker.py` |
| Upload pipeline: limits, dedupe by SHA-256, store original, one transaction | `studyhub/ingest.py` |
| Subject-scoped BM25 search (SQLite FTS5) | `studyhub/retrieval.py` |
| New tables `documents`, `topics`, `chunks`, `chunks_fts` (migration 2) | `studyhub/db.py` |
| Material queries, all filtered by `user_id` and `subject_id` | `studyhub/repo.py` |
| Upload, view, search and remove pages | `studyhub/web/app.py`, `studyhub/web/ui.py` |

Libraries added: `pypdf`, `python-docx`. Originals are kept under `data/uploads/<user id>/<sha256>` (git-ignored).
Limits (environment-configurable): 50 MB per file, 1,500 pages, 8,000,000 characters per subject (raised from 20 MB, 400 pages and 2,000,000 on 20 Sept 2026 after real textbooks of 565 to 961 pages were refused).

## Found while testing, and fixed

- A screenshot of the search page for the real PDF was 11,846 px tall: every word was its own passage. The PDF emits
  `word\n \nword`, and my blank-line splitter treated that as a paragraph break. PDF paragraphs now split only on two or
  more consecutive newlines. A regression test reproduces the pattern (the old splitter gives 6 fragments where 1 is
  expected), and the real-PDF test now checks passage length.
- Earlier in the phase, two of my own tests were wrong (an expected error message, and a ligature test the PDF builder
  could not express); both were corrected, not the code.

## Known limits — read before relying on this

- **Search returns weak matches.** Terms are OR-ed, so a question like "how does inorder traversal … work" also returns two
  unrelated PDF passages that only contain "work". Search is for finding candidates; the answering layer (A3) must apply a
  relevance test and abstain, and that is not built yet.
- **Topics from PDFs need bookmarks.** A PDF without an outline is one topic (the student is told). Headings are not guessed
  from PDF text. The real-world PDF above has no outline.
- **Repeated header/footer text** in PDFs is kept as-is (the sample PDF repeats a heading line).
- **No OCR.** Scanned PDFs are reported and stored with 0 passages.
- **Legacy `.doc`, images, ZIPs are refused**; only PDF, DOCX and plain text are accepted. Markdown is read as text.
- **DOCX has no page numbers** (Word does not store them); passages cite their heading path instead.
- Upload size is checked from the declared `Content-Length` before parsing and again after reading; a client that streams
  without a length header is still bounded by the read limit but is parsed first.
- Only Edge was used in the browser test. No load testing; tested with documents of a few pages, not a 400-page textbook.
- Web URLs are not implemented (phase D).
